| 2026-10-27 | Relative imports under `src/` use no file extension (`from '../meta/client'`), not the `.js` extension TS/NodeNext convention suggests for an `.ts` file | A live `next dev` smoke test showed Turbopack cannot resolve `'../foo.js'` back to `foo.ts` (`Module not found`), even though `tsc` and `vitest` both resolved it fine. `tsconfig.json` already uses `moduleResolution: "Bundler"`, which supports extensionless imports — this is the idiomatic form for that setting and what Next.js itself expects |

See `docs/DAY0-VERIFICATION.md` §1 for the raw finding |
| 2026-10-27 | `supabase/migrations/0003_service_role_grants.sql` explicitly grants `service_role` SELECT/INSERT/UPDATE/DELETE on every table | Discovered via the same smoke test: `service_role` has `BYPASSRLS` but was never given a table-level grant (this project's default ACL for tables created by `postgres` only gives `anon`/`authenticated`/`service_role` TRUNCATE/REFERENCES/TRIGGER) — every server-side write failed with "permission denied" until this migration. Not a SPEC deviation, but worth recording since it is easy to silently reintroduce when a new table is added without an equivalent grant |
| 2026-10-27 | `src/lib/tools/europe-pmc.ts` parses publication type from a flat `pubType` string ("research-article; journal article"), not a `pubTypeList.pubType` array | Live call to `GET /europepmc/webservices/rest/search` on 2026-10-27 returned `pubType` as a single "; "-separated string on every result checked; `pubTypeList` was absent. Code accepts both shapes (falls back to `pubTypeList.pubType` if ever present) so an API change wouldn't silently break classification |
| 2026-10-27 | Module 02 connectors (PubMed esearch/esummary, Europe PMC search/fullTextXML, Crossref works lookup) use plain `fetch` with hand-rolled rate limiting/caching (`src/lib/tools/rate-limiter.ts`, `ttl-cache.ts`), not a third-party HTTP/cache library | All three are public, unauthenticated REST APIs with simple JSON/XML responses; a dependency wasn't needed. Verified field shapes live for all three (esummary `pubtype`/`articleids`, Europe PMC `pubType`, Crossref `update-to`/`issued.date-parts`) rather than only trusting older docs/examples |
| 2026-10-27 | Reorganized the flat `src/lib/**` tree (used in every decision/commit up to this point) into a modular monolith: `src/shared/<package>/` for cross-cutting infrastructure, `src/modules/<NN-name>/` per architecture module, each with exactly one `index.ts` public API; enforced by `scripts/check-module-boundaries.mjs` in `pnpm lint`. Updated SPEC §12's repository layout and added `docs/architecture/00-overview.md` "Module boundaries" | User-requested, explicitly to avoid "deified", hard-to-decompose code as modules 04/05/07/08/09/12 get built later. Confirmed scope with the user first: a single-process modular monolith (plain function calls between modules), not HTTP boundaries or separate deploys — the latter would have contradicted SPEC §12's own "simpler than a monorepo for 9 days" decision. The boundary checker itself caught one real violation on the first run (a `shared/agents` test importing module 08's schema), fixed before this commit |
| 2026-10-27 | `POST /api/runs` now runs module 01's `structure -> plan -> retrieve -> dedupe -> classify` slice synchronously inside the same request, via a new `createRunAndRetrieve` composition, rather than waiting for the resumable/SSE execution module 01 describes | That execution model (stage_outputs persistence, SSE) isn't built yet; a live smoke test measured ~13-14s end to end for an `algorithm`-intent request. Re-checked against `docs/DAY0-VERIFICATION.md` §4 (Vercel's own docs): Hobby's 300s default-and-max duration limit is not actually at risk from this alone — the real cost today is no incremental feedback during the wait and no resumability on a crashed/disconnected request, not a hard platform ceiling. (An earlier version of this entry and of `SECURITY.md` overstated this as a Vercel timeout risk before this re-check; corrected here.) Tracked in `SECURITY.md`'s Known gaps until streaming/chunked execution exists |
| 2026-10-27 | `CandidateSourceSchema` (`src/modules/02-retrieval/schemas/retrieval.ts`) gained an optional `pubTypes: string[]` field | `applyPubmedTypeOverride` (module 02) needs a source's PubMed publication types to force `kind` after classification, but `CandidateSource` had nowhere to carry them from the retrieve step through to the classify step. A minimal, backward-compatible addition (optional field, no existing consumer broken) rather than a parallel side-channel map keyed by `tempId` |
| 2026-10-27 | The retrieve step (`src/modules/02-retrieval/retrieval/execute-plan.ts`) only executes `pubmed`/`europe_pmc` search-plan queries; `guideline`/`web`/`local` queries are recorded as skipped, not executed | `web` needs the Meta API's own `web_search` tool invoked through an agent, not a plain deterministic `fetch`; `guideline`/`local` need a configured domain allow-list (`fetch_url_text`, still empty by default per `SECURITY.md`) and a local-protocol document pool (module 10), neither built yet. Logged as a known gap rather than faked with an empty/placeholder result |
| 2026-10-27 | `run-retrieval.ts`'s pipeline stops at `deduplicateCandidates`; `resolveVersions`/`selectTopNWithDiversity`/`buildCoverageReport`/`scoring/score.ts` (module 02 curation, already built and unit-tested) are not wired in | Each needs candidates grouped by issuer+topic first; nothing in the codebase computes that grouping, and it isn't a well-defined piece to invent without further design (version-resolution's own code comment already flags this as "left to the caller"). Logged rather than wiring in an ungrounded heuristic |
| 2026-10-27 | Reversed the previous day's choice to run `structure->plan->retrieve->classify` synchronously inside `POST /api/runs`: that endpoint now only routes (fast), and a new `GET /api/runs/:id/stream` (SSE) runs the full pipeline (now through `extract`+`verify` too), streaming progress as it happens | User-requested explicitly for time-to-first-token: "orchestrate everything for the smallest possible TTFT ... a robust answer without requiring extreme generation times." Module 01's own architecture doc already specified this POST-fast/GET-stream split (SSE, `band_ready`) — this reverts to what the doc said rather than inventing a new design. The split required a new problem to solve: scenario text is never persisted (CLAUDE.md rule 3), so the SSE route can't recover it from the `runs` row alone — solved with an in-memory, single-use `pendingRunContext` handoff (`src/modules/01-orchestrator/server/pending-run-context.ts`), the same per-process caveat already accepted for the budget guard, not a new persistence of scenario text |
| 2026-10-27 | `band_ready`'s "red-flag and first-action claims first" ordering (module 01) is approximated as "every verified(-pending-support) claim, after sources prioritized by evidence kind (guideline/SR/RCT)" rather than implemented in full | True red-flag/first-action tagging needs the algorithm graph (module 06), not built yet. Logged as an approximation of the real design, not the real thing, so it isn't mistaken for the finished feature later |
| 2026-10-27 | `VerifiedClaimSchema` (`src/shared/domain/claim.ts`) now also requires `verification.support === 'supports'`, not just `quoteFound` | Module 03's `support-judge` (T2) agent isn't built; without this tightening, a claim verified only by the deterministic checks (quote/numbers/retraction/safety) but never judged for support could incorrectly type-check as a displayable `VerifiedClaim`. No existing consumer depended on the looser check (grep-confirmed unused before this change) |
| 2026-10-27 | Claim extraction's `source-classifier`-style metadata-only input gap is now compounded: `extract-and-verify-pool.ts` caps extraction at 10 sources, prioritized by classified `kind` (guideline/local_protocol > systematic_review > RCT > other), rather than running extraction on every deduped candidate | Module 02's real scoring (`scoring/score.ts`) isn't wired in (see above) and running extraction (~9-10s, ~$0.01-0.03 per source, live-measured) on an unbounded pool would make both latency and cost unpredictable. "Prefer stronger evidence first" using the kind classification already produces is a principled, bounded stand-in — logged as a stand-in, not presented as the real ranking |
| 2026-10-28 | `findWebSources` (module 02) is a thin budget-checked wrapper around `metaClient.respond` with `tools:['web_search']`, not a `runAgent` call | `runAgent`'s retry-on-invalid-JSON harness is built for model-authored structured output; `web_search_call.results` (title/url/snippet) is returned by the API itself, already structured — there is nothing for a zod schema to validate here, so forcing this through `runAgent` would add machinery that doesn't apply. User-requested (web crawling for CDC/societies/open-access sources) |
| 2026-10-28 | The default `fetch_url_text` allow-list is a hardcoded curated list (`default-allowed-domains.ts`: CDC, WHO, NICE, AHA/ACC journals, ESC, IDSA, ATS, ACOG, AAP, Cochrane, NCBI Bookshelf, MAGIC), not user-configurable yet | User explicitly asked for "some domains we know by default we can search" plus, later, letting the clinician verify/add their own — the first half is this list; the second needs a settings UI (module 11, not built). Tracked as a follow-up in the file's own comment rather than promised as done |
| 2026-10-28 | `stage_outputs` rows are always INSERTed fresh (never UPDATEd in place), with no unique constraint on `(run_id, stage)`; readers take the most recent row per stage | Keeps a retried stage's history instead of silently overwriting it, and avoids an upsert's read-then-write race; the table's own comment already calls it "resumption state," not a single current snapshot. User-requested (persist initial-attempt progress so a resumed/rerouted request doesn't regenerate everything) |
| 2026-10-28 | `payload_ref` (jsonb) stores the stage's actual output value inline (`{ value, reasons }`), not a pointer into a separate blob store, despite the "_ref" in its name | No blob store exists for this purpose; at this project's scale (CandidateSource[]/Claim[] arrays, a few KB to tens of KB per run) storing inline is the honest Day-1 choice. This is structured, derived output (quotes ≤300 chars, candidate metadata) — never the raw scenario free text or full document text CLAUDE.md rule 3 says must never be persisted, which is a different thing from this product's own verified-claim output that SPEC §8 already designs as persisted data |
| 2026-10-28 | `run-retrieval.ts`'s `planCondition` fallback changed from `??` to `||` with a final `'unspecified clinical condition'` default | Live-tested the new resumability feature and found resuming with no free text could leave every fallback (routerCondition, structure's population, freeText) empty, which crashed `planSearch`'s own `.min(1)` input validation synchronously instead of failing the `plan` stage gracefully. Fixed as part of verifying resumability, not a separate unrelated change |
| 2026-10-28 | UI MVP (module 11) uses `@radix-ui/react-tabs`/`react-dialog` directly, hand-styled with Tailwind, rather than generating components through the shadcn CLI | SPEC §12 names "Tailwind CSS, Radix/shadcn" as the stack; shadcn's CLI scaffolds a larger component set and config than a 2-screen MVP needs. Using Radix primitives directly satisfies the same architectural decision (accessible, unstyled primitives + Tailwind) with less generated surface area to maintain under a hackathon clock — more components can be added the same way, or migrated to shadcn's generator, without re-deciding the underlying primitive library |
| 2026-10-28 | Tailwind CSS v4's CSS-first config (`@theme inline` referencing `:root` custom properties in `src/app/globals.css`), not a `tailwind.config.js` | v4's documented pattern for tokens that must stay runtime-overridable (e.g. a future light-theme override via `[data-theme="light"]`) is exactly this indirection — defining `--color-accent` etc. directly in `@theme` would inline the literal value at build time and break that. No separate JS config file is needed for v4's PostCSS plugin |
| 2026-10-28 | Every claim card and the evidence drawer show a persistent "Not confirmed" chip, never style a claim as "verified" | Module 03's `support-judge` isn't built, so `verification.support` is always `'unknown'` (2026-10-27 entry, `VerifiedClaimSchema` tightening). CLAUDE.md rule 5 ("no unverified but shown" state) and docs/architecture/03's own rule ("support unknown -> drawer-only, marked not confirmed") both require this; the UI enforces it visually rather than relying on a future developer to remember the rule |
